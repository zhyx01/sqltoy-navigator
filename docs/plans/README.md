# 计划文档约定

本目录存放**执行计划文档**。台账（进行中 / 已完成的总览）在仓库根目录的 [`../../PLANS.md`](../../PLANS.md)。

## 命名

```text
YYYY-MM-DD-<小写短横线主题>.md
```

例如 `2026-10-14-harness-bootstrap.md`。日期取**计划开始**的那天，不是完成日。

## 位置与生命周期

```text
docs/plans/            ← 进行中（draft / active）
docs/plans/done/       ← 已完成（done）或已放弃（dropped）
```

状态流转：

```text
draft（方案阶段） → active（执行中） → done（完成）
                                    ↘ dropped（放弃，必须写原因）
```

每次状态变化必须做两件事：

1. 改文档头部的 `状态` 字段
2. 同步 `PLANS.md` 台账里对应的那一行

## 硬性要求

1. **`active` 的计划必须写明「验证方式」。** 写不出验证方式的计划，说明还没想清楚 —— 不许开工。这条是这个目录唯一真正重要的规则。
2. **计划可以改，但只改原文档。** 变更时在末尾「变更原因」里补一句为什么，不要另开一份新文档。
3. **不要删计划。** 放弃也是一种结论，保留它并写明原因。
4. **范围要写「不做什么」。** 边界比清单更能防止跑偏。

## 模板

```markdown
# 计划：<标题>

- 状态：draft
- 创建日期：YYYY-MM-DD
- 完成日期：
- 目标：一句话说清"做完之后什么变了"

## 背景与现状

为什么现在做。现状必须是**可核实的事实**：文件路径、行号、提交号、实测输出。

## 范围

### 要做

- ...

### 不做（边界）

- ...

## 步骤

| 阶段 | 内容 | 验收标准 |
|------|------|----------|
| 1 | ... | ... |

## 验证方式

每个阶段怎么证明它真的成了：命令、期望输出、要人工检查的具体行为。

## 风险与依赖

可能踩的坑；依赖的其它分支 / 改动。

## 决策记录

执行中做的取舍，写清"当时为什么这么选"。

## 变更原因

（后续对计划本身的修改记在这里）
```
