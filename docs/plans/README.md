# 计划文档约定

本目录存放**执行计划文档**。台账（进行中 / 已完成的总览）在仓库根目录的 [`../../PLANS.md`](../../PLANS.md)。

## 命名

```text
YYYY-MM-DD-<中文描述>-<英文短横线主题>.md
```

三段都要有，缺一段就无法同时满足「人能一眼看懂」和「能按主题检索」：

| 段 | 写法 | 作用 |
|----|------|------|
| `YYYY-MM-DD` | 计划**开始**那天，不是完成日 | 目录按文件名排序即时间序 |
| `<中文描述>` | 中文，写清「这件事是什么」；允许夹英文术语（`SQLID`、`Harness`） | 人不用打开文件就知道内容 |
| `<英文短横线主题>` | 全小写、`-` 分词 | `grep`、URL、跨平台工具链的安全检索键 |

示例：

```text
2026-10-15-未定义的-SQLID-错误-unresolved-sqlid-error.md
2026-10-14-Harness-工程改造-harness-bootstrap.md
2026-08-31-悬浮提示三处问题修复-hover-hint-fix.md
```

**改名要带历史。** 重命名一律用 `git mv`（不要 `mv` + 另建新文件），否则 git 会把一次改名看成「删一个、加一个」，计划的演进过程断在这里。

**改名的同时必须同步引用。** 文件名被这些地方引用，缺一处就会留下死链：

```bash
grep -rn "<旧文件名>" --include=*.md .
```

覆盖范围通常包括：`AGENTS.md`、`PLANS.md`、`docs/index.md`、`ARCHITECTURE.md`（目录树示意图）、`docs/plans/README.md` 的「现有计划」表、其它计划文档正文里的交叉引用。

**这条规则目前还没有机械化校验**（harness 阶段 4 会补一条：文件名必须同时含中文段与全小写英文段，且以 `.md` 结尾）。在那之前靠人工对照本节的三段式表格。

## 位置与生命周期

| 目录 | 放什么 |
|------|--------|
| `docs/plans/` | 只有本文件（写法约定） |
| `docs/plans/active/` | **还没结束**的计划：待开工、进行中 |
| `docs/plans/completed/` | **已经结束**的计划：已完成、已放弃（归档） |

一句话规则：**没结束的留在 `active/`，一结束就移进 `completed/`**。执行到一半要离开、过几天回来接着做，就去 `active/` 找。

状态与位置的对应关系：

| 状态 | 含义 | 文档所在目录 |
|------|------|--------------|
| 待开工 | 方案已写好，还没动手 | `active/` |
| 进行中 | 正在执行 | `active/` |
| 已完成 | 做完并且验证过 | `completed/` |
| 已放弃 | 主动放弃，必须写明原因 | `completed/` |

每次状态变化必须做两件事：

1. 改文档头部的「状态」字段
2. 同步 `PLANS.md` 台账里对应的那一行

## 硬性要求

1. **进行中的计划，末尾必须写「当前进度与下次续接」。** 中文，三句话以内：做到哪一步、下次从哪一步接着做、有什么卡着。目的是让执行者在任何时候离开、过几天回来，只看文档最后一段就能接上 —— 写不出这三句，说明计划还不够具体。
2. **`进行中` 的计划必须写明「验证方式」。** 写不出验证方式的计划，说明还没想清楚 —— 不许开工。这条是这个目录唯一真正重要的规则。
3. **计划可以改，但只改原文档。** 变更时在末尾「变更原因」里补一句为什么，不要另开一份新文档。
4. **不要删计划。** 放弃也是一种结论，保留它并写明原因。
5. **范围要写「不做什么」。** 边界比清单更能防止跑偏。这一节还有第二个作用：它是 [`../conventions.md`](../conventions.md) 第 14 节「最小修改」在**本任务上**的实例化 —— 开工前先读它，执行时只改这里点到的位置，范围外的问题报而不改。
6. **正文一律用中文描述。** 英文只允许出现在代码标识符、类名、方法名、命令、文件路径和目录名里；凡是**说明性文字** —— 状态、目标、结论、原因、步骤、风险 —— 全部用中文写。目录名 `active` / `completed` 属于路径的一部分，是这条规则的例外。
7. **不自动提交。** 写计划、改计划、按计划落码，都只落盘到工作区；`git add` / `git commit` / `git push` 等用户明确说了再做，提交范围也由用户指定（例如「只提交功能代码，不带 harness 文档」）。因此本目录与 `PLANS.md` 里写「已提交 / 未提交」时，一律指**事实状态**，不代表下一步会自动提交。规则全文见 [`../conventions.md`](../conventions.md) 第 12 节。

## 模板

```markdown
# 计划：<标题>

- 状态：进行中
- 创建日期：YYYY-MM-DD
- 完成日期：
- 目标：一句话说清"做完之后什么变了"

## 背景与现状

为什么现在做。现状必须是**可核实的事实**：文件路径、行号、提交号、实测输出。

## 范围

### 要做

- ...

### 不做（边界）

- ...

## 步骤

| 阶段 | 内容 | 验收标准 |
|------|------|----------|
| 1 | ... | ... |

## 验证方式

每个阶段怎么证明它真的成了：命令、期望输出、要人工检查的具体行为。

## 风险与依赖

可能踩的坑；依赖的其它分支 / 改动。

## 决策记录

执行中做的取舍，写清"当时为什么这么选"。

## 变更原因

（后续对计划本身的修改记在这里）

## 当前进度与下次续接

（中文，三句话以内：做到哪一步、下次从哪接着做、有什么卡着。
计划结束后改成最终结果与遗留事项。）
```
