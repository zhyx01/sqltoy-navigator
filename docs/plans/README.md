# 计划文档约定

本目录存放**执行计划文档**。台账（进行中 / 已完成的总览）在仓库根目录的 [`../../PLANS.md`](../../PLANS.md)。

## 命名

```text
YYYY-MM-DD-<小写短横线主题>.md
```

例如 `2026-10-14-harness-bootstrap.md`。日期取**计划开始**的那天，不是完成日。

## 位置与生命周期

| 目录 | 放什么 |
|------|--------|
| `docs/plans/` | 只有本文件（写法约定） |
| `docs/plans/active/` | **还没结束**的计划：待开工、进行中 |
| `docs/plans/completed/` | **已经结束**的计划：已完成、已放弃（归档） |

一句话规则：**没结束的留在 `active/`，一结束就移进 `completed/`**。执行到一半要离开、过几天回来接着做，就去 `active/` 找。

状态与位置的对应关系：

| 状态 | 含义 | 文档所在目录 |
|------|------|--------------|
| 待开工 | 方案已写好，还没动手 | `active/` |
| 进行中 | 正在执行 | `active/` |
| 已完成 | 做完并且验证过 | `completed/` |
| 已放弃 | 主动放弃，必须写明原因 | `completed/` |

每次状态变化必须做两件事：

1. 改文档头部的「状态」字段
2. 同步 `PLANS.md` 台账里对应的那一行

## 硬性要求

1. **进行中的计划，末尾必须写「当前进度与下次续接」。** 中文，三句话以内：做到哪一步、下次从哪一步接着做、有什么卡着。目的是让执行者在任何时候离开、过几天回来，只看文档最后一段就能接上 —— 写不出这三句，说明计划还不够具体。
2. **`进行中` 的计划必须写明「验证方式」。** 写不出验证方式的计划，说明还没想清楚 —— 不许开工。这条是这个目录唯一真正重要的规则。
3. **计划可以改，但只改原文档。** 变更时在末尾「变更原因」里补一句为什么，不要另开一份新文档。
4. **不要删计划。** 放弃也是一种结论，保留它并写明原因。
5. **范围要写「不做什么」。** 边界比清单更能防止跑偏。
6. **正文一律用中文描述。** 英文只允许出现在代码标识符、类名、方法名、命令、文件路径和目录名里；凡是**说明性文字** —— 状态、目标、结论、原因、步骤、风险 —— 全部用中文写。目录名 `active` / `completed` 属于路径的一部分，是这条规则的例外。

## 模板

```markdown
# 计划：<标题>

- 状态：进行中
- 创建日期：YYYY-MM-DD
- 完成日期：
- 目标：一句话说清"做完之后什么变了"

## 背景与现状

为什么现在做。现状必须是**可核实的事实**：文件路径、行号、提交号、实测输出。

## 范围

### 要做

- ...

### 不做（边界）

- ...

## 步骤

| 阶段 | 内容 | 验收标准 |
|------|------|----------|
| 1 | ... | ... |

## 验证方式

每个阶段怎么证明它真的成了：命令、期望输出、要人工检查的具体行为。

## 风险与依赖

可能踩的坑；依赖的其它分支 / 改动。

## 决策记录

执行中做的取舍，写清"当时为什么这么选"。

## 变更原因

（后续对计划本身的修改记在这里）

## 当前进度与下次续接

（中文，三句话以内：做到哪一步、下次从哪接着做、有什么卡着。
计划结束后改成最终结果与遗留事项。）
```
